# board-cy — 板级合同与 AI 硬件上下文

## 模板与实例的关系

本 Skill 是**方法论模板**：它不绑定任何特定板子。每块具体板是一份「实例」——由一份机器可读合同 `board-contract.json` 加一组 `references/*.md` 组成。**先确认你正在处理哪块板的实例**：

- 当前工作区若已实例化本 Skill（有 `board-contract.json` 与配套 references），就读那块板的合同。
- 若没有，先读 `references/INSTANCE-GUIDE.md` 按步骤为当前板建立实例，或明确询问用户要用哪块板的合同。
- 目标项目可以自选内部板型标识，但必须明确映射到实例合同声明的硬件基线；同一块板的产品名、固件板型别名、PCB 丝印可能不同，但不能用来推断多套不同的电气设计。

## 定位

把本 Skill 当作当前板的权威知识来源。它回答「这块板是什么、物理连了什么、哪些边界不能破坏、哪些内容仍未知」，让用户查询开发板资料，也让正在执行其他开发任务的 AI 快速读对硬件。

本 Skill 的职责在交付板级硬件事实、证据边界和安全约束时结束。用户另行要求开发时，Agent 可以依据总体任务继续创建或修改代码，但该授权来自用户请求、目标项目约定及其他适用 Skill，不来自本 Skill。不要因为调用本 Skill 就自行创建工程、改代码、构建、烧录或监视串口。

除非用户明确把某个工程指定为资料核对对象，否则不要读取、套用或推荐工作区里的其他应用工程；它们不是开发板知识来源、示例模板或默认实现。

## 先执行这套上下文工作流

1. **确认需要哪部分板级信息**
   - 判断用户是在直接查询开发板资料，还是让 AI 为另一个开发、诊断或评审任务加载硬件上下文。
   - 只围绕用户提到或目标任务实际涉及的资源取数；板上存在某资源不等于本次必须讨论或初始化它。
   - 如果用户只询问开发板资料而未指定工程，就停留在本 Skill 的 references 与合同，不到工作区搜索项目。
   - 如果用户明确要求核对某个项目，只读取该项目中与板型、引脚或板级约束直接相关的声明；不借机扩展为开发或重构任务。

2. **按任务读取事实**
   - 身份、版本别名和证据优先级：读 `references/identity-and-authority.md`。
   - GPIO、方向、有效电平或 UART：读 `references/pinout.md`。
   - BOOT、下载、恢复或端口问题：必须读 `references/boot-flash-recovery.md`。
   - 电源域、共享外设、唤醒或睡眠：读 `references/power-and-peripherals.md`。
   - 需要区分板级事实与项目自定义项：读 `references/project-boundaries.md`。
   - BOM、DNP、已知缺口或批次风险：读 `references/known-gaps-and-errata.md`。
   - 需要核对项目源码声明与合同一致性：运行 `scripts/check_board_baseline.py`（只读）。

3. **整理可交付的板级上下文**
   - 硬件层只保存 SoC、存储、GPIO、电气方向、有效电平、共享电源、板载外设和物理操作。
   - 项目层保存按键动作、消抖参数、交互语义、协议、分区、休眠策略、工具链版本等，明确标为「由目标项目决定」。
   - 输出时给出本次相关的板型身份、GPIO/方向/有效电平、安全边界、已知未知项和来源；不替目标项目选择策略，也不从其他工程推断默认值。

4. **按需做只读声明核对**
   - 只有用户要求核对明确项目时，才运行 `scripts/check_board_baseline.py <项目目录> --contract <合同.json>`；以 `--help` 显示的参数为准。
   - `FAIL` 表示与当前板级合同冲突，先修正或拿到新的硬件证据；`WARN` 表示静态扫描无法确认或发现潜在风险，不能自动改写成失败。
   - 普通头文件保护、未选构建分支和不被识别的代码形态都可能让声明退出 PASS/FAIL；出现 `BUILD_BRANCH_UNSELECTED` 或 `PIN_DECLARATIONS_NOT_FOUND` 时，必须说明对应内容未被验证。
   - 脚本只是启发式只读扫描器。退出码 `0` 只表示没有发现已建模的 `FAIL`，不证明原理图、电气安全、构建图、装配状态或真机行为。

5. **回答或交还上下文**
   - 直接查询时，只回答有证据的板级事实，同时标明未知项、被取代说法和必要安全边界。
   - 作为开发上下文时，把整理结果交还给总体开发任务；不在本 Skill 内规定代码结构、组件选择、业务行为、构建命令或发布流程。
   - 总体任务若涉及工具链环境、build、flash、monitor 或设备验身，再由 Agent 使用对应工具链 Skill（如 ESP-IDF 生态用 `esp-idf-cy`）。本 Skill 只提供板级专属事实，不构成执行或写入授权。
   - 必须区分资料已确认、静态声明未见冲突、构建通过、烧录通过、应用日志通过和用户观察到物理现象。没有相应证据时不要升级结论。

## 板的不可破坏合同（读当前实例的合同）

每个实例的 `board-contract.json` 定义本板的不可破坏合同，包括：

### BOOT 与正常启动
- 当前板进入下载模式、退出下载模式、恢复正常启动的**唯一正确操作**，以合同 `boot` 段为准。
- 板上是否有独立的用户 RESET/EN 按键，以合同为准；不要让用户寻找不存在的按键。
- 若实物与合同不符，先检查板型、批次或硬件异常，不要静默退回旧操作或通用教程。

### 关键资源
- 按键、编码器、LED、电源域、USB、麦克风、扬声器、唤醒脚等关键 GPIO 与有效电平，以合同 `pins` 段为准。
- 共享电源域（如外设电源开关）的上电时序与安全要求，以合同 `power` 段为准；没有充分证据的时序值保持 UNKNOWN，目标项目必须依据器件规格或测量完成资格确认。
- 完整映射、有效电平和限制只在合同与 references 维护，不在应用代码或回答中凭记忆补齐。

## 事实冲突处理

按以下顺序处理板级事实，且记录被取代关系：

1. 硬件负责人明确确认的当前实板行为或可复现 HIL 证据。
2. 可追溯的当前批次 ECAD/BOM/装配资料与板级专项测试。
3. 随实例打包的原理图、PCB 快照与硬件说明。
4. 实例的 `board-contract.json` 及其合同测试；它是前述证据的规范化机器副本，若与原始证据冲突则必须修订，不能自证正确。
5. 用户明确指定的目标项目声明；它只能描述项目选择，不能覆盖物理连线。
6. 历史迁移文档、旧版本代码、临时归档和网络上的通用教程。

低优先级材料只能提供线索，不能覆盖更高优先级事实。发现冲突时指出来源、采用哪一条及原因；没有足够证据时保留 `UNKNOWN`，不要做「最像通用做法的猜测」。

## 项目边界

- 本 Skill 不创建或初始化工程，不编写或修改业务代码，不选择项目架构，也不负责 build、flash、monitor 或 HIL。
- 在更大的开发任务中调用本 Skill，只表示 Agent 应读取并遵守板级事实；开发动作是否执行仍由用户请求、项目约定和其他适用 Skill 决定。
- 本 Skill 不定义按键动作语义、外设交互方向、协议、分区、NVS、OTA、联网或产品逻辑。
- SoC、存储容量等是板级事实；分配策略、分区表和具体工具链版本是目标项目合同。
- 既有应用即使使用同一块板，也不能成为板级知识或其他项目的隐式模板。只有用户明确要求核对或移植某一应用时，才可把该应用作为独立输入读取，并仍以本 Skill 的硬件合同为上限。
- 若目标项目声明与板级事实冲突，报告冲突并交还总体任务处理；若新实板证据反驳合同，暂停引用该事实并按变更门更新实例合同。

## 完成标准

完成一次板级资料回答或 AI 上下文加载前，确认：

- 板型身份没有因多个别名被误判成多套不同电气设计。
- 本次涉及的 GPIO、有效电平、外设方向和限制可追溯到当前合同与 reference。
- 共享电源、BOOT 等硬护栏已随上下文交付。
- 板级事实、目标项目策略和仍未知内容被清楚区分。
- 静态扫描、构建、烧录、日志和真机证据没有互相冒充。
- 新发现的硬件事实附来源、日期和验证方式；未知项仍明确为未知。
- 没有把调用本 Skill 当成创建项目、改代码、构建或写入设备的授权。

## 禁止事项

- 不教当前板用户通用教程里的「按住 BOOT + 上电」等未经验证的操作（以实例合同为准）。
- 不把共享电源脚当成只控制单一外设的开关，也不把其他工程中的延时值当成已证明的硬件最小值。
- 不从历史日志中取第一条 GPIO 命中作为当前真值。
- 不硬编码串口端口名或用端口名代替设备身份。
- 不因截图中出现料号就声称已有最终 BOM、DNP 或量产验收。
- 不主动搜索、引用或继承任何既有应用工程的按键动作、命名、协议、分区、依赖版本、电源策略或实现架构。
- 不把本 Skill 描述成项目脚手架、固件生成器、构建器、烧录器或完整开发板 SDK。
